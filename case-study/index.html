Case study · front-end focused full-stack

A print-ready catalogue, built in the browser.

For a UK food wholesaler’s internal sales portal I worked on the tools that turn a range of around 2,500 products into an A4 catalogue: a millimetre-exact page engine, a flyer editor whose prices and QR codes come from the product database, and a compressor that makes the finished PDF small enough to send.

The real code and data belong to the company, so this is a clean rebuild on the same stack around a fictional wholesaler, Harbourline Wholesale, with generated products, prices, photos and posters.

The problem

Sales reps needed a catalogue that is never out of date.

A catalogue put together by hand goes stale the day a price changes. The portal already held the products, prices and photos. The job was to turn them into pages that look designed, print exactly, and stay small enough to email to customers, without anyone touching code or a design tool.

Exact A4

Consistent margins and coloured bands on every page, printed straight from the browser.

Hundreds of photos

Some missing, some slow, one or two broken, and printing must not start before they arrive.

No code for users

Office staff change layout, covers and flyers with switches, sliders and drag and drop.

Shareable output

A browser-printed catalogue embeds full-size photos, so the PDF has to be shrunk before it is sent.

What is real and what isn’t

  • The company, brands, products, prices, phone number and web address are invented. Product codes look like HL-10001.
  • Product photos and flyer posters are drawn by code (SVG), not taken from anywhere.
  • No code, data, screenshots, branding or documents from the real system are used. Every file was written for this rebuild.
  • Data lives in memory and resets on restart. There is no login and no cloud storage.
  • Numbers from the real system are marked reported. Every other number on this page was measured on the demo.
01

Module 1 · Catalogue engine and export page

Pages are computed in millimetres, then drawn by React.

Problem

Categories have very different sizes. Starting every small subcategory on a new page wastes paper; cramming everything together makes a page nobody can scan. And the contents page needs page numbers that are only known at the end.

What I built

  • An export page with collapsible sections for cover, layout, contents, products, cards and extras.
  • A one-page preview with a page list on the right and ←/→ keys to flip.
  • Save as PDF: every page rendered as a real 210 × 297 mm box and printed by the browser.

Interesting bits

  • Pure layout functions. No React or DOM inside: products and settings in, page models out. Preview, print and tests all use the same output.
  • Small shelves share a page. A category always starts fresh. A small subcategory moves up under the previous one when at least one full row fits; the rest continues overleaf, marked “continued”.
  • Numbers from the final order. Cover, contents, flyers and category covers are placed first, then every page is numbered once; the contents page links to each page in the PDF.
  • Settings that survive bad input. Saved settings are parsed field by field with zod, so one stale value falls back to its default instead of breaking the page.

    02

    Module 2 · Photo loader and print check

    Hundreds of photos, six at a time, with a report before printing.

    Problem

    If every image starts loading at once, the photo host gets flooded and the print dialog opens over half-empty cards. Users then can’t tell a product that has no photo from one whose photo failed.

    What I built

    • One shared queue for every product photo in the app.
    • A check before printing that waits for the queue, then lists what is missing and what failed, with Retry failed and Print anyway.

    Interesting bits

    • Six in flight, three tries. Errors are retried with back-off; the page on screen jumps the queue.
    • Missing vs failed. A 404 means “fix the data”; a server error means “try again”. They are reported separately because the fix is different.
    • Re-render only what changed. Cards subscribe to their own photo with useSyncExternalStore and are memoised, so moving a slider doesn’t re-render hundreds of unchanged cards.
    03

    Module 3 · Flyers and focal editor

    Product details on a poster, filled from the database.

    Problem

    Marketing makes promotional posters, and the catalogue prints them after the contents page. Typing prices onto a poster means they go wrong the moment the price list changes, and nobody notices a promoted product was discontinued.

    What I built

    • A flyer list: drag to reorder, suspend and resume, with a warning badge when a promoted product can no longer be sold.
    • A full-screen editor where staff search for a product and drop a “focal” on the poster: name, pack size, prices, code and QR code all come from the product record.

    Interesting bits

    • Resolution-independent. Each box is stored as x, y, width and height between 0 and 1 of the poster; text uses container query units, so the same focals print at any size.
    • Snapping with guides. Edges and centres snap to the page and to other focals, with a threshold in screen pixels so it feels the same at every zoom. Alt turns it off.
    • Undo that behaves. History is one state object capped at 40 steps; a whole drag is one entry. Ctrl+Z, Ctrl+Shift+Z, Ctrl+D, Delete and arrow nudging all work.
    • Price change warning. Prices are a snapshot from when the focal was placed; the editor shows when the live price differs and offers a one-click refresh.
    • Optimistic, with rollback. Reorder and suspend update at once and go back to the stored state if the server refuses.

    04

    Module 4 · PDF compression

    Shrink the PDF by resampling only what is too big.

    Problem

    A browser-printed catalogue embeds every photo at full resolution, even when it is printed 5 cm wide. The file is too big to email, and generic online compressors also blur text and QR codes.

    What I built

    • A compress page: upload with a progress bar, a five-step tracker, and a before/after result with a download.
    • A server job that reads the PDF’s drawing instructions to find each photo’s real printed size and resamples it to that, leaving text and vectors alone.

    Interesting bits

    • Measure, don’t guess. A small tokenizer follows the page’s transform matrix to learn how big each image is drawn, including images inside nested forms.
    • Predict before committing. A spread-out sample of up to 40 photos is encoded at each quality level to choose one that should land under the target size.
    • Only replace what shrinks. A photo that would not get at least 8% smaller keeps its original; transparency masks are resized with their image.
    • Safe uploads. Streamed to a temp file with a running size cut-off, checked for a %PDF- signature, one job at a time, results expire after 20 minutes.

    Architecture

    Thin route handlers, pure modules, one source of truth for pages.

    Server components read the catalogue and hand it to one client component per screen, so the first paint already has data. Everything that can be a pure function is one, which is what makes it testable.

    LayerChoices
    FrontendNext.js App Router, React 19, TypeScript, Tailwind CSS 4, dnd-kit (pointer + keyboard), container query units, print CSS (@page, break-after)
    BackendRoute handlers on Node, zod on every request body, streamed uploads, an in-process job queue with polling
    PDFBrowser print for output; pdf-lib to read and rewrite, sharp to resample images
    QualityVitest (unit + property tests), ESLint, strict TypeScript, CI on GitHub Actions: lint, typecheck, test, build

    Key decisions

    The calls that shaped it.

    Print

    Browser print over a PDF library

    Pages are HTML at exact mm sizes, so text stays text: searchable, sharp QR codes, internal links from the contents page. The cost is depending on Chrome’s print engine, which is stated as a limit.

    Layout

    Millimetres, not pixels

    Card sizes are derived from 210 × 297 mm minus header, footer and gaps. Make the header taller and the cards get shorter; nothing overflows.

    Layout

    Dividers paid for by height

    A subcategory ribbon costs space. Cards on that page get slightly shorter (never below 85%) instead of a whole row being dropped.

    Testing

    Property tests for the engine

    Over 300 random catalogues per option set: every product appears once and in order, no page has more rows than the grid, categories never share a page.

    Flyers

    Store geometry as fractions

    0..1 of the poster instead of pixels, so a focal placed on a laptop prints in the same place on A4.

    Flyers

    Snapshot prices, warn on change

    A flyer is a promise made on a date. The price is kept from placement, and the editor shows when the live price differs instead of silently changing a printed offer.

    Photos

    One queue, two kinds of failure

    Missing and failed photos need different fixes, so the print check reports them separately and only offers a retry for failures.

    Compression

    Resample to printed size

    The target resolution comes from how big a photo is drawn on the page, not a fixed pixel width, so small thumbnails shrink a lot and full-page photos keep their detail.

    Before and after

    What changes for the people using it.

    Without the tool

    • Prices and codes retyped into a design file.
    • The whole document re-flowed by hand when the range changes.
    • Posters printed with whatever price was typed on them.
    • Large PDFs sent through an online compressor.

    With the tool

    • The catalogue is generated from the product data, with covers and contents.
    • Layout changes are switches and sliders, previewed page by page.
    • Flyer prices come from the product record, with warnings for discontinued lines and price changes.
    • Compression runs inside the portal and keeps text sharp.

    This compares workflows. It is not a measured time saving.

    My role

    What I did on the real system.

    I was a junior developer in a two-person team, working mostly on the front end (roughly 60% front end, 30% back end, 10% database and deployment). My manager reviewed every pull request.

    On the real portal I built the flyer list and the focal editor, worked on the catalogue export page, and built the PDF compression feature. I used an AI coding assistant for parts of the work, mainly the compression feature; I reviewed and shipped what went in.

    What this rebuild does better

    • Unit and property tests, and CI. The original had no automated tests.
    • Uploads streamed to disk with a size cut-off, instead of buffered in memory.
    • Focals warn when a price changes; the original kept the old price silently.
    • Keyboard-sortable lists, and dialogs that trap focus and close on Escape.

    What I’d do next

    • Store jobs in a database table so a restart doesn’t lose them.
    • Visual regression tests of printed pages with Playwright.
    • Let the contents page flow onto a second page for larger ranges.
    • Automated accessibility checks in CI.

    Run it yourself

    Two commands, then open localhost.

    No accounts, keys or database. The data is seeded in memory when the server starts. Node 20 or newer.

    # install and start
npm install
npm run dev          # http://localhost:3000

# checks (the same ones CI runs)
npm run lint
npm run typecheck
npm test
npm run build
